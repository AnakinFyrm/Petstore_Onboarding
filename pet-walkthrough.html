01petstore-api/

petstore-api — 数据唯一的真源

给定的 FastAPI + PostgreSQL 应用（被轻度扩展）。全系统里唯一被允许读写数据库的组件；所有校验规则在这一层用 Pydantic 强制执行，坏数据在到数据库之前就被拒绝。

文件作用
app/config.py一个 Settings，从 .env 读 database_url，10 行。
app/database.py建表 DDL + 连接/事务管理（psycopg，同步）。
app/models.py两个字符串枚举：Species、Availability。
app/schemas.pyPydantic 模型 + 所有业务校验规则（真正的核心）。
app/crud.py手写参数化 SQL：搜索、查询、创建、购买。
app/main.pyFastAPI 路由，把 crud 的异常翻译成 HTTP 状态码。
app/seed.py首次启动时灌入 8 条示例宠物数据。

校验规则写在模型里，不写在业务代码里 app/schemas.py

PetBase 用 Field(min_length=…)、ge=、gt= 这类约束，把 README 里罗列的每一条规则 （名字 2–50 字符、体重 > 0、尾长 ≥ 1、价格 > 0……）直接写进类型定义。三个自定义校验器补上纯类型标注做不到的逻辑：

app/schemas.py
@field_validator("tags", mode="before")
@classmethod
def normalize_tags(cls, tags: list[str]) -> list[str]:
    seen: dict[str, str] = {}
    for tag in tags:
        cleaned = tag.strip()
        if not cleaned:
            raise ValueError("Tags may not be blank.")
        key = cleaned.lower()
        if key in seen:
            raise ValueError(f"Duplicate tag: {cleaned}")
        seen[key] = cleaned
    return list(seen.values())

@model_validator(mode="after")
def species_requires_specific_species(self) -> "PetBase":
    if self.species == Species.other and not self.specific_species:
        raise ValueError("A specific species is required when species is 'other'.")
    return self

normalize_tags 用一个 dict（而不是 set）去重，是为了在拒绝重复标签的同时保留标签原本的大小写和出现顺序—— key 只用来判重，真正存回去的是 seen[key] 里那个原始字符串。 species_requires_specific_species 是一条跨字段规则：只有当 species == other（比如示例数据里的刺猬 Sprout）时才强制要求 specific_species。

PetSearch 里还有一条容易漏掉的一致性检查：min_age_months 不能大于 max_age_months，价格区间同理—— 这条规则如果不在这里挡住，会变成一次注定查不出结果、却不会报错的搜索。

购买是「查库存 → 建订单 → 改状态」三步事务 app/crud.py

app/crud.py
def purchase_pet(conn: Connection, pet_id: int) -> PetRow:
    pet = get_pet(conn, pet_id)
    if pet["availability"] != "available":
        raise PetNotAvailableError(f"Pet {pet_id} is not available for purchase.")

    order = conn.execute(
        "INSERT INTO orders (pet_id, price_eur) VALUES (%(pet_id)s, %(price_eur)s) RETURNING *",
        {"pet_id": pet_id, "price_eur": pet["price_eur"]},
    ).fetchone()

    conn.execute(
        "UPDATE pets SET availability = 'sold' WHERE id = %(id)s",
        {"id": pet_id},
    )
    return order

注意订单里的 price_eur 是从刚查出来的 pet["price_eur"] 取的，从不接受调用方传入的价格—— 这是「价格永远只能来自商店」这条规则在数据库这一层的落地。db_session()（database.py）用 try/except/finally 包住这两条 SQL：任何一步出错就整体 rollback()，不会出现「订单建了、库存却没改」的半成品状态。

list_pets 用字符串拼接生成 SQL 的 WHERE 子句，但拼的只是列名和条件片段，真正的值全部走 %(name)s 参数占位符—— 这就是为什么它头顶那行 # noqa: S608 注释敢说「标识符是静态的，值是参数化的」，可以安全地关掉 SQL 注入检查。

FastAPI 只做一件事：把内部异常翻成状态码 app/main.py

七个路由里最值得看的是异常映射：PetNotFoundError → 404，PetNotAvailableError → 409， PetSearch 构造失败 → 422。lifespan() 用 run_in_threadpool 在应用启动时依次跑 init_db()（建表）和 seed_if_empty()（灌种子数据），因为这两个函数底层是同步的 psycopg 调用，直接在异步的 lifespan 里跑会卡住事件循环。

02pet-client/

pet-client — 唯一懂 HTTP 细节的地方

全系统里（除 petstore-api 自己）唯一知道 petstore-api 的 URL、HTTP 动词和状态码的模块。它的存在就是为了让上层（MCP 服务器）永远不用碰 httpx。

文件作用
models.py镜像 petstore-api 的 Pydantic 模型（故意不共享 import）。
exceptions.py把 HTTP 状态码翻译成 Petstore 语义的异常。
client.py基于 httpx.AsyncClient 的三个方法：搜索、查询、购买。

models.py 的文件头注释解释了一个容易让人疑惑的设计：为什么不干脆 from app.schemas import Pet 直接复用？ 因为 pet-client 和 petstore-api 是两个独立部署单元（未来是两个容器），运行时根本不共享 Python 解释器—— 它们唯一共享的是「通过 HTTP 传输的数据形状」，所以这里手写了一份结构相同、但完全独立的模型副本。

状态码 → 语义异常的翻译表 client.py

client.py · _request()
try:
    response = await self._http.request(method, path, **kwargs)
except httpx.RequestError as exc:
    raise StoreUnavailableError(f"Could not reach petstore API: {exc}") from exc

if response.status_code == 404:
    if not_found_pet_id is not None:
        raise PetNotFoundError(not_found_pet_id)
    raise StoreUnavailableError(f"Unexpected 404 from petstore API: {path}")

if response.status_code == 409:
    if not_found_pet_id is not None:
        raise PetNotAvailableError(not_found_pet_id)
    raise PurchaseFailedError(response.text)

if response.status_code == 422:
    raise InvalidRequestError(response.text)

if response.status_code >= 500:
    raise StoreUnavailableError(f"Petstore API returned {response.status_code}: {response.text}")

调用方（MCP 服务器）从此只需要认识 PetNotFoundError、PetNotAvailableError、InvalidRequestError、 StoreUnavailableError、PurchaseFailedError 这五个类，永远不用处理 httpx.HTTPStatusError 或裸的连接异常。 这正是 agent 能「诚实地解释失败」的前提——失败原因在很早的一层就已经被归类成了人能理解的语言。

构造函数里 transport 参数的注释值得一读：它是专门给测试开的口子（换成 httpx.MockTransport 让请求不真的上网）， 并且解释了一个 httpx 的坑——必须在构造 AsyncClient 时就传入 transport，事后重新赋值 self._http._transport 是不生效的，因为 httpx 还有一张独立的 _mounts 代理路由表会抢在默认 transport 前面被查询。

03pet-mcp/

pet-mcp — 暴露给 agent 的三个工具，仅此而已

一个跑在 stdio 上的 MCP 服务器（src/pet_mcp/server.py，222 行）。它是 agent 触达 Petstore 的唯一入口，只导出三个工具，且购买工具本身带着一道代码写死的确认关卡。

购买确认关卡在代码里，不只在 docstring 里 server.py

server.py · pet_mcp_purchase_pet()
@mcp.tool(annotations=_PURCHASE_ANNOTATIONS)
async def pet_mcp_purchase_pet(pet_id: int, confirm: bool) -> dict[str, Any]:
    if not confirm:
        raise ToolError(
            "CONFIRMATION_REQUIRED: call pet_mcp_get_pet first to show the customer this "
            "pet's current name, price and availability, get their explicit confirmation to "
            "buy it at that price, then call pet_mcp_purchase_pet again with confirm=True."
        )
    try:
        async with _petstore_client() as client:
            order = await client.purchase_pet(pet_id)
    except PetNotFoundError as exc:
        raise ToolError(f"PET_NOT_FOUND: {exc}") from exc
    except PetNotAvailableError as exc:
        raise ToolError(f"PET_NOT_AVAILABLE: {exc}") from exc
    ...
    return order.model_dump(mode="json")

这里的关键在于 if not confirm: raise ToolError(...) 这一行是执行到的代码，不是写给模型看的说明文字—— 就算 LLM 完全没理会 docstring 里那一大段「必须先展示价格再确认」的指示、直接用 confirm=False（或者压根不传）调用， 购买依然会在这里被硬拦下来，什么都买不成。三个工具各自的用途：

  • pet_mcp_search_pets — 按任意条件组合搜索/列出宠物；不传参数就是列出全部库存。
  • pet_mcp_get_pet — 拿一只宠物「此刻」的价格和可购买状态；docstring 明确要求在展示价格前、以及购买前都要重新调用一次，因为对话里记住的状态可能已经过期。
  • pet_mcp_purchase_pet — 上面这段代码；扣的价格永远是 petstore-api 当下记录的价格，这个工具没有任何办法接受调用方传入的价格。

工具还各自带了 ToolAnnotations：只读工具标 readOnlyHint=True, idempotentHint=True（可以放心反复调用）， 购买工具反过来标 destructiveHint=True, idempotentHint=False（会改变商店状态，不能被无副作用地重试）—— 这是 MCP 协议里客户端用来判断「这个工具能不能安全重试」的标准标注方式。

04pet-aes/

pet-aes — 跟宠物店本身无关的「agent 运行时」

通用、可复用的 agent 基础设施，只有两个核心模块：agents.py（怎么把声明变成一个 pydantic_ai.Agent）和 service.py（怎么安全地运行它）。改编自组织内部一个真实在跑的 AES 参考实现。

AgentSpec：一个 agent 的全部定义写在一处 agents.py

agents.py
@dataclass(frozen=True)
class AgentSpec:
    name: str
    prompt_path: Path
    tools: tuple[str, ...] = ()
    optional_tools: tuple[str, ...] = ()
    output_schema: type[BaseModel] | None = None
    description: str = ""
    subagents: tuple[str, ...] = ()

    @property
    def declared_tools(self) -> frozenset[str]:
        return frozenset(self.tools) | frozenset(self.optional_tools)

tools 是「必须存在，缺了就报错」的本地工具名；optional_tools 是「有就用，没有就悄悄跳过」—— pet-agent 用的正是 optional_tools，因为它的三个工具全部来自一个启动时可能连不上的 MCP 子进程。

真正的安全边界：把 MCP toolset 过滤到白名单 agents.py · _filtered_toolsets()

agents.py
def _filtered_toolsets(spec: AgentSpec, toolsets: Sequence[AbstractToolset[Any]]) -> list[AbstractToolset[Any]]:
    allowed = spec.declared_tools

    def _allow(_ctx: RunContext[Any], tool_def: ToolDefinition) -> bool:
        return tool_def.name in allowed

    return [ts.filtered(_allow) for ts in toolsets]
为什么这段代码是全项目的安全核心

MCP 服务器暴露多少工具，agent 能用多少工具，这两件事被这四行代码彻底解耦了。就算 pet-mcp 以后被改成暴露 20 个工具， _filtered_toolsets 也只会放行 PETSTORE_AGENT_SPEC.optional_tools 里声明过的那三个名字—— agent 不会「顺带」获得新能力，除非有人显式改动 pet-agent 自己的 spec。这就是 README 说的 「pet-mcp 以后暴露更多工具，也永远不能悄悄扩大 agent 的能力」在代码里的样子。

HostedAgentService：一次对话的运行边界 service.py

handle_message(message, session_id=...) 是外部唯一能调用的入口：它自动把某个 session_id 之前的 ModelMessage 历史续上、调用 agent.run()、把最新历史存回 self._histories 字典、 返回 result.output。任何异常都在这里被 except Exception: self._logger.exception(...) 兜住， 换成一句 DEFAULT_FALLBACK_MESSAGE（“Sorry, something went wrong on our end…”）—— 调用方（CLI）永远看不到裸异常、堆栈、或者可能带密钥的内部报错。request_limit 会变成 UsageLimits(request_limit=10)，给「模型想犯糊涂、工具调用无限循环」这件事设了个硬上限。

05pet-agent/

pet-agent — 真正的购物助手 + 你敲命令的地方

五个项目里最大的一个：既是把 PETSTORE_AGENT_SPEC 交给 pet-aes 托管的 agent 定义，也是你在终端里打字的那个 CLI，外加配置、多 LLM 后端、日志和遥测。

agent.py：一个 spec + 一个 stdio 子进程 agent.py

agent.py
PETSTORE_AGENT_SPEC = AgentSpec(
    name="petstore-agent",
    prompt_path=_PROMPTS_DIR / "system.md",
    optional_tools=(
        "pet_mcp_search_pets",
        "pet_mcp_get_pet",
        "pet_mcp_purchase_pet",
    ),
    description="Conversational Petstore shopping assistant: helps a customer browse, filter, and buy pets.",
)

def build_pet_mcp_toolset(settings: Settings) -> MCPToolset:
    env = {**os.environ, "PETSTORE_API_BASE_URL": settings.petstore_api_base_url}
    transport = StdioTransport(
        command="uv",
        args=["run", "--project", settings.pet_mcp_project_dir, "pet-mcp"],
        env=env,
    )
    return MCPToolset(transport)

这个模块自己没有任何 @agent.tool 本地函数，也从不 import pet_mcp 或 pet_client—— 「agent 只能通过 MCP 服务器操作、不得绕开它」这条规则不是靠自觉遵守，而是代码结构上就没给绕开留出口子。 build_pet_mcp_toolset 用 uv run --project <pet-mcp 目录> pet-mcp 把 pet-mcp 整个当子进程拉起来， 并显式透传完整的父进程环境变量——因为 MCP 的 stdio 传输默认只继承一个很小的“安全变量”子集，在 Windows 上尤其不够用， 这也解释了为什么这台机器上这个项目能正常跑通。

config.py：三层环境变量叠加 + 「LLM 是否真的可用」判定 config.py

config.py · Settings.llm_enabled
@property
def llm_enabled(self) -> bool:
    backend = self.llm_backend.strip().lower()
    if backend == "anthropic":
        return self.anthropic_api_key is not None
    if backend in {"openai", "openai_compat"}:
        return bool(self.llm_model) and (self.openai_api_key is not None or bool(self.openai_base_url))
    if backend == "azure":
        return all((
            self.azure_openai_api_key is not None,
            self.azure_openai_endpoint,
            self.azure_openai_deployment,
        ))
    return False

配置本身按优先级叠三层：真实进程环境变量 > .env.$APP_ENV（按 dev/test/production 选定的档案）> .env.shared（提交进仓库的、不含密钥的公共默认值）。llm_enabled 把「关闭」和「配置不全」并成同一种 「没准备好」状态，好处是服务永远只有一种安全的降级模式，而不是在第一次真正调用 LLM 时才崩溃。 README 里提到的「已知偏差」也在这里能对上号：LLM_BACKEND=openai_compat + OPENAI_BASE_URL=https://openrouter.ai/api/v1， 走的是 OpenAI 兼容协议直连 OpenRouter，而不是文档原本要求的 Litellm 代理。

llm/client.py：一个工厂函数，四个可选后端 llm/client.py

create_llm(settings) 按 llm_backend 的值分发到 _build_anthropic / _build_openai （同时覆盖 openai 和 openai_compat 两个值） / _build_azure，每个都返回一个 pydantic_ai.models.Model。它从不抛异常：任何一个构建函数失败，都会被外层 except Exception 捕住、记一条 warning、返回 None——调用方（agent.py 的 run_agent）自己决定「模型是 None」该怎么办 （目前是直接 RuntimeError 拒绝启动）。pydantic_ai 相关的 import 全部写在函数体内部而不是模块顶部， 这样即使没装某个 provider 的可选依赖，这个文件本身依然能被正常 import、单元测试也能正常跑。

system.md：模型被允许做什么、绝不允许做什么 llm/prompts/system.md

系统提示词把「购买」拆成一个五步、每次都要重新来一遍的固定流程：

  1. 锁定对象 —— 顾客指向一只具体的宠物。
  2. 重新查询 —— 调用 pet_mcp_get_pet 拿最新数据，哪怕上一秒才查过一次。
  3. 展示当下事实 —— 把刚查到的名字、价格、可购买状态说给顾客听。
  4. 要求明确确认 —— 「听起来不错」「我可能会买」都不算数，只有针对具体宠物和价格的明确肯定才算。
  5. 确认之后才下单 —— 且只对刚确认的那一只下单。

提示词里还有一条经常被写代码的人忽略、但对「诚实」至关重要的规定：「除非购买工具刚刚返回了这个结果，否则永远不要说购买成功、 报出订单号、或描述收据」——这直接堵死了模型在工具调用失败后凭空编一个「已为您下单」的可能性。

cli.py：欢迎语、退出词、一个 while 循环 cli.py

CLI 本身完全不决定任何 Petstore 相关的事——它只负责三件事：打印 WELCOME、识别 exit/quit/q/:q/bye/goodbye 这几个退出词、把每一行非空输入转发给 service.handle_message(message, session_id=...) 并原样打印回复。展示宠物列表、报价、 要求确认、收据或失败说明——这些全部发生在 service.handle_message 内部，cli.py 自己不格式化、不判断。

⚠ 发现一处会导致程序无法启动的语法错误

run_dialogue() 里捕获 Ctrl-D / Ctrl-C 的那一行写成了：

except EOFError, KeyboardInterrupt:

这是 Python 2 的写法，在 Python 3（这个项目锁定的 3.14）里是 SyntaxError：多个异常类型必须用括号包起来。 实测用 ast.parse() 解析这个文件会直接报错 multiple exception types must be parenthesized—— 也就是说，整个 pet_agent.cli 模块现在导入不了，docker compose run --rm pet-agent 会在启动阶段就崩掉。

修复方式：把这一行改成 except (EOFError, KeyboardInterrupt):（加一对括号）。

alerting.py / observability.py / logging_config.py

这三个是运维基础设施，跟 Petstore 业务逻辑没有关系：alerting.py 定义了一个 Alerter 协议 （默认实现 LogAlerter 只是把告警写进日志，未来可以换成 Slack/PagerDuty 而不用改调用方代码）； observability.py 的 setup_telemetry 是「令牌门控 + 失败即放行」——没配 LOGFIRE_TOKEN 就什么都不做，遥测本身出错也只记警告、绝不阻止服务启动； logging_config.py 只是转发到 _service_core_shim（下面会讲）。

顺带发现：两个当前没被真正用到的文件

db.py（连接池 + init.sql 应用器）和 llm/schemas.py（一个泛化的 ExtractedItem 抽取模型）只被各自的单元测试引用，在 agent.py／cli.py 的真实运行路径里完全没人 import 它们。 这符合项目结构的既定分工——pet-agent 从不直接碰数据库，那是 petstore-api 的职责——它们看起来是脚手架模板 （.copier-answers.yml 表明这五个子项目都是从同一份公司内部模板生成的）留下的通用样板，还没被清理。不是 bug，但如果要精简代码库，这两个文件是可以先看的地方。

_service_core_shim/：一个临时替身

config.py 和 logging_config.py 头部注释都写明：这几行 import 本该指向公司内部私有仓库 fyrm_service_core（提供分层 env 文件加载、结构化日志、脱敏等能力），但这份检出目前没有那个仓库的读权限， 所以先用 pet_agent._service_core_shim 里一份本地替身顶上。以后拿到权限，官方说法是「只需要改两行 import」就能切回去， 不影响任何调用方代码。

06pet/docker-compose.yml

根目录编排：一条命令拉起三个容器

整个仓库唯一「写清楚」的启动路径。三个 service：db、petstore-api、pet-agent（pet-mcp 被直接打进 pet-agent 的镜像里，作为它内部启动的子进程，而不是第四个容器）。

  • db —— postgres:19beta1-alpine，数据落在命名卷 petstore-db-data 里，docker compose down（不带 -v）不会清掉它，只有显式 down -v 才会。
  • petstore-api —— depends_on: db (service_healthy)，等数据库健康检查通过才启动，暴露在宿主机的 :8000。
  • pet-agent —— stdin_open: true + tty: true，要用 docker compose run --rm pet-agent（不是 up）启动，才能把你真正的终端接上去；密钥只通过 env_file: .env（被 .gitignore 和 .dockerignore 双重排除）注入运行中的进程，从不烘进镜像。

容器内 PETSTORE_API_BASE_URL 被显式设成 http://petstore-api:8000（走 Compose 网络的服务名解析）， 是这个文件里唯一跟「Docker 之外直接跑」不同的地方——脱离 Docker 时默认值是 http://localhost:8000。

除了逐模块讲解，读代码时用 ast.parse() 和交叉引用核实了两处值得你知道的情况。

会阻塞启动 pet-agent/src/pet_agent/cli.py:115 — Python 2 语法的多异常捕获

改成 except (EOFError, KeyboardInterrupt):
